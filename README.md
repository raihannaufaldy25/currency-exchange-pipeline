# Currency Exchange Rate Pipeline

A small end-to-end ETL pipeline that extracts historical currency exchange rates against IDR (Indonesian Rupiah), transforms them into an analysis-ready format, loads them into a PostgreSQL database, and runs analytical SQL queries on top of the result. Built as a portfolio project to practice core data engineering concepts: API extraction, data transformation, database loading, and SQL-based analysis (with cloud storage integration planned as a next step).

## Overview

This pipeline collects daily exchange rate data for 6 foreign currencies (USD, SGD, AUD, JPY, KRW, MYR) against the Indonesian Rupiah, using the [Frankfurter API](https://frankfurter.dev/) — a free, open-source currency data API with no authentication required.

```
Frankfurter API
      |
      v
  extract.py  ---->  raw_data/*.json   (raw API response, unmodified)
      |
      v
 transform.py ---->  processed_data/*.csv  (cleaned, validated, with inverse_rate column)
      |
      v
   load.py    ---->  PostgreSQL (table: exchange_rates)
      |
      v
  analyze.py  ---->  sql/*.sql queries (day-over-day change, weekly average,
      |              volatility, overall performance)
      v
(planned)  raw_data/*.json  ---->  AWS S3  (see "Future Improvements")
```

## Setup & How to Run

### 1. Clone and install dependencies
```bash
git clone https://github.com/raihannaufaldy25/currency-exchange-pipeline.git
cd currency-exchange-pipeline
python -m venv .venv
source .venv/bin/activate   # or .venv\Scripts\activate on Windows
pip install -r requirements.txt
```

### 2. Set up PostgreSQL
This project was developed against a locally installed PostgreSQL instance. Create a database (e.g. `currency_db`) before proceeding to the next step.

### 3. Configure environment variables
Copy `.env.example` to `.env` and fill in your database credentials:
```bash
cp .env.example .env
```

### 4. Adjust `config.yaml` if needed
```yaml
currency:
  base: "IDR"
  quote:
    - "USD"
    - "SGD"
    - "AUD"
    - "JPY"
    - "KRW"
    - "MYR"

date:
  from: "2026-04-01"
  to: "2026-06-30"
```

### 5. Run the pipeline, in order
```bash
python src/extract.py
python src/transform.py
python src/load.py
python src/analyze.py
```

## Analysis Layer

Once data is loaded into PostgreSQL, `analyze.py` runs a set of SQL queries (stored separately under `sql/`) to answer specific questions about the data:

| Query | Question it answers | Key SQL concept |
|---|---|---|
| `pct_rate_change.sql` | How much did each currency move compared to the previous day? | Window function (`LAG`) |
| `weekly_average.sql` | What was the average rate per currency, per week? | Date bucketing (`DATE_TRUNC`) |
| `volatility_analysis.sql` | Which currency moved the most relative to its own average? | Coefficient of Variation (`STDDEV / AVG`) |
| `overall_performance.sql` | Which currency strengthened/weakened the most over the whole period? | Self-join with subqueries (`MIN`/`MAX` date) |

Queries are kept as standalone `.sql` files rather than inline strings in Python, so they can be read, tested, or edited independently of the codebase.

## Design Decisions

A few decisions I made along the way, and the reasoning behind them:

- **Base currency is IDR, with a computed `inverse_rate` column.** The Frankfurter API only supports one base currency per request. Rather than making 6 separate API calls (one per target currency as base), I request once with `base=IDR` and compute `inverse_rate = 1 / rate` during transformation to get the more intuitive "1 USD = X IDR" representation. This keeps API usage minimal while still producing readable output.
- **Data validation is intentionally lightweight.** Since Frankfurter is a stable, official data source, I check for null values and non-positive rates and log a warning if found, rather than building automatic imputation logic. Given the very low likelihood of bad data from this source, adding imputation would add complexity without meaningful benefit — I'd rather surface a data quality issue than silently guess a value.
- **`if_exists="replace"` when loading to PostgreSQL.** This makes the load step idempotent — re-running the pipeline with the same date range always produces the same end state, without duplicate rows accumulating. The trade-off: any manually-added indexes or constraints on the table would be dropped on each run, since pandas recreates the table from scratch. Acceptable for this project's scale.
- **Dates are explicitly parsed on load (`parse_dates`).** CSV files don't preserve column data types — without this, the `date` column would be stored as text in PostgreSQL. This caused a real bug during development: `DATE_TRUNC()` failed outright, and while `LAG() OVER (ORDER BY date)` happened to still sort correctly (because `YYYY-MM-DD` text sorts the same as chronological order), that was incidental, not something to rely on. Fixing the type at the loading stage avoids this issue for every downstream query, rather than casting it repeatedly wherever it's used.
- **Volatility uses Coefficient of Variation, not raw standard deviation.** Raw `STDDEV` is affected by the scale of each currency's rate (USD's rate is in the thousands, KRW's is around 11) — comparing raw standard deviations across currencies would mostly reflect scale differences, not actual relative volatility. Dividing by the mean (`STDDEV / AVG`) normalizes this, making the comparison fair across currencies with very different magnitudes.
- **Credentials are never hardcoded.** Database credentials live in `.env` (gitignored). AWS credentials use the standard `~/.aws/credentials` file (via `aws configure`), so they never touch the codebase at all.
- **Shared logic lives in `utils.py`.** `read_config()`, `get_db_engine()`, and shared path constants are used by multiple pipeline stages, so they're centralized in one place instead of duplicated across `extract.py`, `transform.py`, `load.py`, and `analyze.py`.

## Known Limitations

- Raw data is currently only stored locally; cloud backup to AWS S3 is planned but not yet implemented (see Future Improvements).
- Scheduling is not yet automated (planned: a cron job to run the pipeline daily — see Future Improvements).
- The pipeline currently processes one fixed date range at a time, configured via `config.yaml`, rather than incrementally appending new days.
- `LAG()`-based day-over-day comparisons assume no missing dates in the sequence; a gap in the data (e.g. a source outage) would silently compare non-adjacent days without flagging it.
- No automated tests yet.
